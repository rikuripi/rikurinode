## Important findings (each fails the pass)

**I-1 (Security & funds / mutation): the claim code's entropy is unproven.** Survivors `crates/rikuri-control/src/claim.rs:123:21: replace < with >` (and `< with <=`) and `claim.rs:124:64: replace % with /` in `generate`. With `byte > 248` only 7 symbols are ever drawn, with `byte / 31` only 8: a code of ≈28–30 bits instead of the ≈49.6 bits §0b records, and every test still passes (`a_code_is_ten_symbols_of_the_alphabet_shown_in_groups` only checks membership). A security property is claimed without a test holding it. Minimal correction: a unit test that generates e.g. 300 codes and asserts every one of the 31 `ALPHABET` symbols appears (kills `>` and `/`); the 1/256 bias of `<=` toward `A` is below what a count can see and may be recorded as accepted.

**I-2 (Bugs, recovery / mutation): the state layer's "absent vs unreadable" classification is untested.** Survivors `crates/rikuri-control/src/state.rs:99:23` (`StateDir::read`) and `state.rs:131:23` (`StateDir::remove`): `replace match guard e.kind() == io::ErrorKind::NotFound with true`. With them, any I/O error reads as "no file": for `ca.key.der`/`ca.crt.der` a read fault would re-issue the CA that §0b says is never re-issued (silently, apart from `ca_created=true` in the log); `claim::finish` would report success with the claim file still present. The recovery evidence in §4 covers only the JSON-parse flavour (`owner.rs`, `session.rs`). Minimal correction: unit tests in `state.rs` that `read`/`remove` of a name that is a directory (EISDIR, deterministic even as the namespace's mapped root) return `Err(StateError::Io { .. })`, not `Ok(None)` / `Ok(false)`.
